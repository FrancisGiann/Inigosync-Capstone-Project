# PayMongo checkout setup and rollout

Customer bookings now start with a short physical-court hold. The browser sends the selected court or lane, time, and payment choice to `paymongo-checkout`; the server checks availability and rates, then creates **one PayMongo session for the cart**. A booking and calendar block are created only after a signed PayMongo payment event is verified. A redirect from PayMongo is never proof of payment. A cancelled or expired session keeps its hold until the provider confirms that the session has closed.

## Required server configuration

Set these as Supabase Edge Function secrets in the existing Supabase project
`xrlwtnwamboucihsamrr`. This project remains the app's database in test mode;
no test database or schema migration is required. Test payments are simulated,
but the existing signed webhook will record them as paid and confirm
reservations in this database. Those records do not represent collected money.

| Secret | Purpose |
| --- | --- |
| `PAYMONGO_SECRET_KEY` | Use the PayMongo `sk_test_` key for sandbox operation or `sk_live_` for live operation. This key is project-wide and selects the mode for all PayMongo Edge Functions that use it. |
| `PAYMONGO_PUBLIC_KEY` | Matching key for the selected mode, used server-side by QR Ph payment flows. |
| `PAYMONGO_WEBHOOK_SECRET` | Signing secret for the webhook registered in the selected PayMongo mode and pointed at this project's `/functions/v1/paymongo-webhook`. |
| `APP_BASE_URL` | Exact HTTPS origin of the customer and staff pages. |

Supabase supplies `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` to Edge Functions. Keep all provider and service-role credentials off the browser, repository, and owner settings page. The owner page changes the deposit percentage and enabled payment methods in `app_settings`; it only **reports** PayMongo connection, webhook, and last confirmed payment status.

The expiry worker's shared token is generated in Supabase Vault by migration `20260926170234_enable_checkout_expiry_cron.sql`. The scheduled job sends that token to `paymongo-expire-checkouts`; the worker validates it through a service-only database function. Do not copy the token into frontend code or a second secret.

## Test-mode checkout in the existing project

Customer booking checkout expands to `card`, `gcash`, `paymaya` (Maya), and `grab_pay` when this function reads an `sk_test_` key. When the owner has enabled QR Ph, new customer carts also offer `qrph` in test mode for both full and deposit payments at any amount accepted by PayMongo. PayMongo may add a processing fee to the final customer total, so the payer must check the total on the hosted page. PayMongo says its test QR codes can still accept real money; showing a test QR is therefore a real-money risk even though the API key is in test mode. Use PayMongo's simulator to authorize, fail, or expire a test QR payment; do not scan or pay the QR code. With an `sk_live_` key, checkout continues to use only the owner-enabled Card, GCash, and QR Ph methods. Staff walk-in, staff balance, and payment-health flows keep their existing method lists.

The method list is saved with each checkout attempt when the PayMongo session is created. Changing this code or the owner's QR Ph setting does not add QR Ph to an already-created hosted session. An existing unpaid checkout remains tied to its saved session and payment-method list; check its provider status and hold before starting a replacement.

**Observed sandbox behavior (2026-10-27):** in the PayMongo TEST dashboard, two one-time Payment Links (₱1 and ₱1,300) each showed only QR Ph in customer checkout; both links were archived after inspection. The TEST Payment Methods settings page also stated that managing payment methods is unavailable in test mode. A provider-level V2 Checkout Session probe accepted the requested methods (HTTP 200, `livemode: false`) and its hosted page rendered QR Ph, Card, GCash, GrabPay, and Maya, but not ShopeePay. No payment was made, and the unpaid session was expired. ShopeePay is unavailable in this TEST account and is omitted. This probe did not test reservation settlement. The temporary `Inigosync Test` Supabase project used for the provider probe was deleted; the app uses only the original project.

The Edge Function configuration has one `PAYMONGO_SECRET_KEY`, shared by the customer checkout, webhook, expiry worker, and other PayMongo flows. Switching it to `sk_test_` puts those provider calls into test mode; while it is set, live PayMongo transactions cannot be created or verified by these functions. Keep the existing `PAYMONGO_WEBHOOK_SECRET` matched to an enabled TEST webhook at this project's `/functions/v1/paymongo-webhook` before starting checkout. The `paymongo-checkout` code retains the live owner-enabled method list when it reads an `sk_live_` key and expands only customer booking checkout when it reads `sk_test_`. A signed simulated test payment will be recorded as paid and confirm the reservation in the existing database without collecting money. Treat that database as sandbox data until the live credentials and webhook are restored together.

ShopeePay is not requested by test-mode customer checkout. QR Ph is offered for test-mode customer carts at any provider-supported amount, including deposits, only when the owner has enabled it. A PayMongo test QR may process a real transaction. Do not scan or pay it; use the PayMongo simulator and verify the signed webhook/booking outcome rather than assuming payment from the redirect.

PayMongo's current Hosted Checkout API uses `paymaya` and `grab_pay` as the API values for Maya and GrabPay. Its test guide says wallet authorization is simulated through the PayMongo test page. PayMongo also warns that test-mode QR Ph codes are real QR codes: do not scan or pay them; use a returned test simulator URL when available. ## Webhook and payment behavior

Register a PayMongo endpoint for both `checkout_session.payment.paid` and `payment.paid` at `https://xrlwtnwamboucihsamrr.supabase.co/functions/v1/paymongo-webhook`. Use the PayMongo TEST endpoint/signing secret while running in sandbox mode, and switch the endpoint and secret back together before live payments. The handler verifies the raw-body signature, test/live mode, PHP gross amount, and provider session/payment intent, and deduplicates the event. `paymongo-webhook` and the cron worker have Supabase JWT verification disabled because they use separate signed authentication. Customer and staff checkout functions require an authenticated Supabase JWT.

The default deposit is 50%; the owner may change it and enable Cash, Card, GCash, and QR Ph independently. At least one online method must stay enabled. New checkouts snapshot their total and deposit charge, so later settings or court-rate edits cannot reprice them. Bowling uses `/set`: each set costs one set rate and reserves one hour on the selected lane.

Staff may collect a deposit booking's remaining balance in Cash through the authenticated check-in action. For PayMongo, staff start a separate balance checkout. The webhook records that balance, then staff confirm attendance. Neither a successful browser redirect nor an unverified payment may increase `amount_paid`.

For a walk-in customer paying by QR Ph, staff choose **QR Ph**. The server creates a PayMongo Payment Intent for the server-priced order total and attaches a QR Ph Payment Method. The staff screen displays PayMongo's actual amount-specific dynamic QR image in both live and test mode. Test mode has a prominent warning: **Do not scan or pay this test QR; use the simulator for test confirmation.** Scanning a PayMongo test QR can process a real transaction. The screen links to the sandbox simulator only when PayMongo returns a trusted `https://test.paymongo.com` URL; if it is missing or untrusted, the image remains available for inspection, the warning remains visible, and no simulator link is offered. Staff wait for the signed `payment.paid` event, verified as QR Ph, and the confirmed acknowledgment before issuing the entry pass. GCash availability is independent from QR Ph availability. Cash tender and change are validated against the authoritative order total in the same database transaction and included in the saved payment and acknowledgment.

For the QR and cash rollout, apply `20261016130000_walkin_qrph_intents_cash_tender.sql` after the existing walk-in checkout recovery migration, then apply `20261016152145_add_qrph_sandbox_simulator.sql` and `20261017045802_persist_walkin_qrph_livemode.sql`. The last migration stores the verified PayMongo mode with each QR attempt; older saved QR attempts without a recorded mode fail closed and need owner reconciliation. Deploy the updated webhook and `staff-walkin-checkout` function, then deploy the static site and staff dashboard stylesheet. Set both matching PayMongo key types as Edge Function secrets. Verify that the test QR image is displayed with the do-not-scan/pay warning, the trusted sandbox simulator opens when provided, payment status remains pending until the signed webhook confirms it, and live QR payment, expiry, retry, and persisted cash receipt paths work before using live keys. PayMongo documents the QR Ph test-mode real-transaction hazard and simulator flow in its [testing guide](https://docs.paymongo.com/docs/payment-acceptance-testing).

## Rollout checks

1. Configure the three secrets and verify the owner Payment Configuration page reports an API connection and ready webhook.
2. Test a full-payment cart and a deposit cart with PayMongo test credentials. Confirm the bookings appear only after the signed webhook, and that one cart creates one checkout.
3. In staff Walk-In Management, verify the actual test QR image is displayed beside the prominent do-not-scan/pay warning. Open the trusted simulator link, choose a test result, then check payment status; no acknowledgment should appear until the signed payment webhook confirms payment. Confirm an untrusted or missing simulator URL is not linked and the warning remains visible.
4. Test cancellation and expiry; verify the hold is removed only after PayMongo reports the session expired. Check duplicate webhook delivery creates no extra payment or booking.
5. Test two customers choosing the same physical court at the same time, two bowling sets on one lane, and Cash and PayMongo balance collection at staff check-in.
6. Review any older unpaid pending bookings individually. Existing attempts remain eligible for provider reconciliation; do not delete or mark them paid without checking PayMongo.

If PayMongo credentials, webhook, or the app return origin are missing, **keep the revised customer checkout unpublished**. The database and Edge Functions may be deployed first; their missing-configuration responses prevent a customer from creating an unpaid booking. The scheduled worker also reports unconfigured until `PAYMONGO_SECRET_KEY` is present. Once checkout is configured, publish the frontend, test with PayMongo test mode, and only then plan a separate live-key launch.

An ambiguous checkout creation stays held for review. Search PayMongo by the attempt UUID without hyphens (`reference_number`) and close any provider session before releasing its court hold. The worker moves an unattached creating attempt to review after 23 hours rather than assuming it can safely expire it.
