# Independent reservation QA review

Reviewed 2026-09-25. The reviewer examined live schema, policies/grants, current ledger aggregates, customer/staff UI tests, and each follow-up issue as it was addressed.

## Findings resolved

- Mutable court names and duplicate normalized listing names could misidentify reservations. Reservations now store `court_listing_id`, and normalized listing names are unique.
- Stable unit IDs with blank or stale labels could diverge from the legacy occupancy ledger. Before-write normalization now sets the canonical listing and unit labels from the IDs; normalized unit labels are unique per listing.
- Court/resource retirement or mapping edits could strand pending PayMongo checkouts or silently release one resource from a multi-resource/wildcard reservation. Active reservations now prevent listing/resource retirement and mapping edits; the serialized refresh checks every preexisting `(source, resource)` hold before rebuilding.
- A rebuild could encounter duplicate `(source, resource)` pairs when a legacy wildcard reservation reached the same shared resource through multiple units. The refresh query now deduplicates identical pairs.
- Inventory read failures could expose static, quantity-derived fallback units in customer/staff booking views. Booking selectors fail closed when authoritative inventory cannot be loaded.
- PayMongo retry previously depended on a mutable listing label/current rate before looking up a saved attempt. Checkout now uses stable listing identity for new rates and returns an authorized active saved attempt before rate/status/start-time checks. A new attempt still needs an active customer, eligible unpaid booking, future start, and Available hourly rate; RPC access remains service-role-only.

## Multi-item cart follow-up review

An independent follow-up review passed the customer cart changes. ## Admin mapping and access-control follow-up

Independent QA statically confirmed that the owner UI can create physical resources and sport units, then map multiple units to the same resource. The browser fixture also drives the owner page through adding a physical resource and linking a Pickleball unit to a Basketball resource; it passed with mocked Supabase APIs. A follow-up fixture verifies that empty/unverified inventory is omitted from customer and staff booking selectors while verified sports remain selectable. The current 10-zone Pickleball mapping and live occupancy projection are recorded above. A low accessibility issue in repeated unit controls was fixed by adding sport/unit-specific accessible names. Review also found that resource-write policies previously allowed any authenticated admin role even after its profile was marked disabled. Migration `20260925072230_active_admin_resource_write_checks.sql` now requires the caller's profile to remain an admin and not disabled for all three resource configuration tables; active and pending admins retain their existing access. Rollback-only live RLS checks passed for active admin write allowed, disabled admin write denied, and staff/customer writes denied. The transaction left the admin active and created no QA resources. Supabase security/performance advisors reported no new policy-specific warning from this migration; they continue to report pre-existing internal-table, function-grant, and index notices elsewhere in the project.

The independent Pickleball follow-up review passed: all ten active/verified units map to the confirmed 3+3+2+2 physical zones, a pending Basketball Court 2 reservation is visible on Pickleball Courts 1–3, and the customer/staff booking fixture allows separate Pickleball zones while rejecting overlapping host-court use. The review identified two obsolete unmapped Pickleball resources; both had no active reservation holds, and guarded migration `20260925081633_retire_orphaned_pickleball_resources.sql` retired them. The subsequent live audit found 7 active sources, 23 holds, zero missing holds, zero overlap pairs, and no active obsolete resources. Pickleball pricing remains unconfigured by the manager's request to confirm tiers later.

A fresh Supabase security-advisor check then found that the `inigosync_is_admin()` and `inigosync_is_staff_or_admin()` SECURITY DEFINER helpers were callable by `anon` through default/public grants. Migration `20260925082506_restrict_staff_role_helpers.sql` revoked `PUBLIC` and `anon`, retaining execution for `authenticated` and `service_role`. Live privilege checks passed (`anon=false`, `authenticated=true`, `service_role=true` for both), and live policy inspection confirmed the existing staff/admin write policies still target `authenticated`. The follow-up advisor no longer reports anonymous execution for these helpers. Other existing advisories remain: extension-generated custom range constructors have mutable search paths, `btree_gist` is installed in `public`, authenticated-only SECURITY DEFINER RPCs are flagged by the generic linter, and leaked-password protection is disabled in Auth. The reservation functions were reviewed: `court_occupancy` uses an empty search path and requires a signed-in user; active-admin helpers are also restricted to authenticated users.
